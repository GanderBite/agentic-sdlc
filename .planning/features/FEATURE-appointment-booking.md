# Patient appointment booking flow with per-appointment document share

## Summary

Patients pick a specialization, optionally narrow to a doctor, browse available 30-minute slots within a 30-day horizon, choose documents to share, and confirm; the booking transaction reserves the slot via a DB unique constraint and inserts one appointment_document_share per attached document.

## Scope

- Drizzle tables appointment (state, doctor_id, patient_id, slot_id with UNIQUE constraint, specialization_id denormalised, created_at, deleted_at) and appointment_document_share
- RPC route slots.availability filtering by specialization, optional doctor, future-only, ≤30-day horizon, unbooked, non-soft-deleted; joins doctor_specialization
- RPC route appointments.book — single transaction reserving the slot, asserting document ownership, and inserting share rows; relies on DB unique constraint on appointment.slot_id for concurrent-booking conflict resolution returning a friendly HTTP 409
- Service: 30-day horizon enforced both in availability filter and at booking time; specialization_id resolved at booking time from the slot's doctor
- UI multi-step Schedule Appointment form: specialization → optional doctor → slot grid → document picker → confirm
- Vitest unit tests for slot-availability algorithm (filtering rules) and DB-unique conflict mapping; integration test simulating two concurrent bookings


## Out of scope

- Appointment cancellation or rescheduling (brief §8: frozen out)
- Notifications on successful booking
- Per-appointment share of medications/conditions/allergies (all are visible to the doctor by default — see doctor-appointment-summary)
- Slot search beyond 30 days into the future
- Doctor approval / confirmation step (booking is immediately final)


## Acceptance bullets

- POST /api/slots.availability with { specializationId, doctorId? } returns only future, non-soft-deleted, unbooked slots whose owning doctor (a) holds the requested specialization in doctor_specialization AND (b) matches doctorId when supplied AND (c) starts_at ≤ now() + 30 days in the server TZ; results sorted by starts_at ascending and include doctor id + name + specialization id.
- POST /api/appointments.book with { slotId, sharedDocumentIds: [] } and role=patient returns HTTP 201 and the new appointment id when the slot is in the future, unbooked, not soft-deleted, within the 30-day horizon, and every sharedDocumentIds entry belongs to the caller and is not soft-deleted.
- A second appointments.book against the same slotId returns HTTP 409 CONFLICT with a code identifying "slot just taken" and creates no rows; the conflict is generated by the DB UNIQUE(slot_id) constraint on the appointments table — verified by a concurrent integration test that fires two bookings in parallel and observes exactly one 201 + one 409.
- appointments.book with at least one sharedDocumentIds entry owned by another patient returns HTTP 403 FORBIDDEN and creates no rows (asserted by row-count before/after).
- appointments.book with sharedDocumentIds=[] succeeds and creates the appointment with zero appointment_document_share rows.
- The created appointment carries specialization_id resolved from the slot's doctor at booking time (verified by an integration test that later removes the specialization from the doctor and re-reads appointments.get to confirm the value is preserved).
- Attempting to book a slot whose starts_at is more than 30 days in the future returns HTTP 422 VALIDATION with a code referencing the horizon.
- The Schedule Appointment UI walks specialization → optional doctor → slot grid → document picker → confirm; submitting the final step issues exactly one appointments.book request and navigates the patient to an appointment-confirmed view.
