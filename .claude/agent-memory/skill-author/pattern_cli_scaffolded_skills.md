Some MedBrige skills cover libraries that DO NOT live in `node_modules` — they live as project-owned source files copied in by a CLI. Shadcn UI is the canonical example: `components/ui/*.tsx` is generated by `shadcn add` but then committed and edited locally.

**Why:** This is structurally different from a normal framework dependency. There is no upstream version pin to bump; instead each file has an upstream "drift point" the agent must reason about. Re-running the CLI without `--overwrite` is a no-op; with `--overwrite` it silently destroys local edits.

**How to apply** when authoring this kind of skill:

1. State explicitly that source is project-owned (not node_modules), with a Rule like "Commit every generated file to git".
2. Include an explicit edit-vs-wrap decision rule (when to fork the primitive vs wrap it in a composite). Wrappers compose; edit-in-place creates upstream drift that needs management.
3. Document the diff-then-merge recipe (`shadcn diff` + `git stash` + `add --overwrite` + manual re-apply) for pulling upstream changes safely. Send to a `references/customization.md` to keep SKILL.md compact.
4. Document peer-dep awareness — these tools often have transitive runtime deps (Radix for Shadcn) that the CLI auto-installs. Reviewer needs to know they belong in `dependencies`, not `devDependencies`.
5. Pair-skill the styling/theming layer if the tool theme-couples (Shadcn ↔ Tailwind tokens). Cross-reference but do not duplicate — defer to the styling skill for token grammar.
6. Reserve `components/ui/` (or the CLI's destination) for generic primitives only — domain types belong in `components/<feature>/`. Make this an explicit rule.
